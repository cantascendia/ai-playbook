## ✅ spike-1 — PowerShell 工具的 hook stdin 字段名 = `command`

**方法**：本会话用真实 PowerShell 工具跑无害命令，读 PostToolUse 的 trajectory-logger 产物（该 hook matcher 为 `*`，能看到所有工具）。

```bash
# 工具调用：PowerShell   Write-Output "v5-spike-1-powershell-probe"
tail -6 .claude/agent-logs/2026-09-13.jsonl
```

原始输出（节选）：

```json
{"ts":"2026-09-13T10:32:42+09:00","schema":"v3.8","event":"PostToolUse","tool":"PowerShell","file":"","cmd":"Write-Output \"v5-spike-1-powershell-probe\"","session":"974ed2a1-..."}
```

**结论**：`cmd` 字段有值。`lib.mjs readInput` 读的是 `tool_input.command`，故 **PowerShell 工具的 `tool_input` 字段名与 Bash 相同，为 `command`** → adapter 无需为 PowerShell 做字段映射，只需把 `tool_name` 纳入 shell 类白名单并追加 PowerShell 专属 pattern。

**附带证据（P0 的严重性，非理论风险）**：同一 grep 在历史日志命中 **2026-07-02** 两条 `"tool":"PowerShell"` 的 `git add ...` 调用：

```json
{"ts":"2026-07-02T23:01:50+09:00","schema":"v3.8","event":"PostToolUse","tool":"PowerShell","file":"","cmd":"git add docs/ai-cto/REVIEW-QUEUE.md ...","session":"1647dd1a-..."}
```

即 PowerShell 工具**已被实际使用两个多月**，而 `.claude/settings.json` 的 PreToolUse Bash 组 matcher 只写 `"Bash"`
→ bypass / destructive-action / branch 三个 guard 对这条通道**全程零覆盖**。

**影响**：WS0b 步骤 1-3。

## ✅ spike-2 — NotebookEdit 字段名 = `notebook_path`，提取优先级 `notebook_path → path → file_path`

**方法**：从 2.1.178 二进制抓工具参数提取表与路径解析逻辑。

```bash
B=/c/Users/yuril/.local/bin/claude.exe
grep -a -o -E 'filePatternTools:\[[^]]{0,160}\]' "$B"
grep -a -o -E '"notebook_path"in [A-Za-z]\?"notebook_path":\("path"in [A-Za-z]\)\?"path":"file_path"' "$B"
```

原始输出：

```
filePatternTools:["Read","Write","Edit","Glob","NotebookRead","NotebookEdit","Cd"]
"notebook_path"in W?"notebook_path":("path"in W)?"path":"file_path"
```

2.1.91 同一位置另有更明确的提取表（字段语义跨版一致，可作交叉印证）：

```
Read:{label:"path",extract:Wm("file_path")}, Edit:{...file_path}, Write:{...file_path},
NotebookEdit:{label:"path",extract:Wm("notebook_path")}, Bash:{label:"command",extract:Wm("command")}
```

**结论**：

1. `NotebookEdit` 的路径在 `tool_input.notebook_path`；本仓 `lib.mjs:55` 只读 `file_path || path`
   → **NotebookEdit 的路径恒为空字符串，四条文件类红线全部放行**（P1 洞坐实）。
2. Claude Code 自身的优先级是 `notebook_path → path → file_path`；本仓现为 `file_path → path`。
   adapter 应改为**三级且 notebook_path 优先**，与平台一致。
3. `filePatternTools` 含 `Cd`、**不含 `MultiEdit`** → 确认 MultiEdit 是死代码。
   （清理 guards.mjs 的 MultiEdit 专用分支属 WS1 范围，不与 P0 补丁同 PR。）

**影响**：WS0b 步骤 2、WS1（adapter 路径提取三级化）。

## ✅ spike-5 — Codex hook trust：逐条目 sha256，按绝对路径登记

**方法**：读本机 `~/.codex/config.toml`（Codex CLI 0.154.0 的 trust 状态落盘处）。

```bash
grep -n -A3 '\[hooks.state' /c/Users/yuril/.codex/config.toml | head -20
```

原始输出（节选，路径为另一项目）：

```toml
[hooks.state]

[hooks.state.'C:\Users\yuril\OneDrive\Documents\hoyolab-auto-local\.codex\hooks.json:pre_tool_use:0:0']
trusted_hash = "sha256:6eb353e02516845e15f62afe77c20b487e60bda332967348862acc0e94e13a33"

[hooks.state.'...\.codex\hooks.json:pre_tool_use:0:1']
trusted_hash = "sha256:9c1e39458561fc15acb28fb86e6fcd944e25fde9dbb6aaba42e709bc1a86a971"

# 另有 pre_tool_use:0:2 / 0:3 / 1:0 / post_tool_use:0:0 —— 单个项目共 6 条
```

**结论**：

1. Trust 键 = `<hooks.json 绝对路径>:<event 小写下划线>:<matcher 组下标>:<组内 hook 下标>`；值 = 该 hook 条目定义的 sha256。
2. **粒度是逐 hook 条目**而非逐文件：一个项目 6 个条目 = 6 次批准。我们的 `.codex/hooks.json` 有 N 条就要 N 次。
3. **键含绝对路径** → 每个部署项目必须单独批准，无法跨项目复用。
4. 本仓 `ai-playbook` 在该文件中**无任何 trust 记录**（唯一 `ai-playbook` 字符串命中是 OTEL 资源属性，不是 trust 键）
   → 2026-09-10 生成的 `.codex/hooks.json` **从未生效过**，Codex 侧一直是零守护。

**对计划的硬约束**（并入 §6 与 WS2）：

- compile-policy 的 `.codex/hooks.json` 输出必须**稳定排序、无时间戳**，否则每次重新生成都让全部 N 条 trust 失效。
- `cto-doctor` / `FLEET.md` 必须逐项目读这张表判断 `codex_trust`；未命中即红字「Codex 侧零守护」，**绝不标 ✓**。
- 应**压缩 hooks.json 条目数**（更少的 matcher 组 + 单一 dispatch 入口），直接降低人工批准次数。

**影响**：WS2 步骤 3/6、§6 Fleet、eval 099、drill 07。

## ✅ spike-6 — agy hooks 契约（stdin camelCase / stdout decision / matcher = step type）

**方法**：读 agy 1.2.2 内置 skill 的官方文档，并从 agy 二进制抽 step type 枚举。

```bash
D=~/.gemini/antigravity-cli/builtin/skills/agy-customizations/docs/hooks.md
sed -n '132,220p' "$D"
grep -a -o -E 'CORTEX_STEP_TYPE_[A-Z_]+' <agy 二进制> | sort -u   # 122 个
```

### 6a. 输入契约（文档原文）

```json
{
  "toolCall": { "name": "run_command", "args": { "CommandLine": "npm test" } },
  "stepIdx": 19,
  "conversationId": "ec33ebf9-0cba-4100-8142-c61503f6c587",
  "workspacePaths": ["/path/to/workspace"],
  "transcriptPath": "/path/to/workspace/.gemini/antigravity/transcript.jsonl",
  "artifactDirectoryPath": "/path/to/workspace/.gemini/antigravity/artifacts",
  "modelName": "auto"
}
```

> 文档强调所有 JSON 键为 **camelCase（protojson）**；但工具参数键是 **PascalCase**（`args.CommandLine`）。
> `transcriptPath` / `artifactDirectoryPath` 的目录名随形态而变：CLI = `antigravity-cli/`、2.0 = `antigravity/`、IDE = `antigravity-ide/`。

**结论（解掉一个已知风险）**：payload 自带 `workspacePaths[]`
→ agy adapter **可直接取 repo root 注入 `ctx.cwd`**，不必依赖 hooks.json 所在目录做相对推断。
这消除了宪法/迁移批评家指出的「agy 侧 `isAiPlaybookSelf(ctx.cwd)` 与 `forbiddenPattern(normCwd)` 静默失效」风险。

### 6b. 输出契约（文档原文）

```json
{ "decision": "ask", "reason": "...", "permissionOverrides": ["command(npm test)"] }
```

- `decision`（必填）：`allow` / `deny`（硬阻断）/ `ask` / `force_ask`
- `overwrite`（可选）：**浅层 top-level 合并**改写工具参数后再执行，并通知 agent 哪些键被 hook 改写

**结论**：agy 的 deny 语义完整，且比 Claude 多 `force_ask`；`overwrite` 与 Claude 的 `updatedInput` 同位。
v5 **只用 `deny` / `allow`** 以保持三平台裁决一致（`ask` 在 Codex 侧不支持，用了会造成平台不对称）。

### 6c. matcher = step type，命名 = 去 `CORTEX_STEP_TYPE_` 前缀 + 小写

文档举例 `run_command` / `view_file` / `browser_.*`，二进制中对应 `CORTEX_STEP_TYPE_RUN_COMMAND` / `_VIEW_FILE` / `_BROWSER_*`
→ **命名规则确认**。matcher 支持正则（`browser_.*`）与 `*`/`""`（匹配全部）。

**122 个 step type 中与红线相关的面**（本 spike 最大收获 —— agy 的守护面远不止 `run_command`）：

| 红线面 | 相关 step type |
|---|---|
| 命令执行 | `run_command`、`shell_exec`、`send_command_input`、`run_extension_code` |
| **git 专用** | `git_commit`（独立步骤，绕过类 flag 未必经 `run_command`） |
| 文件写（候选） | `propose_code`、`file_change`、`write_blob`、`edit_notebook` |
| 文件破坏 | `delete_directory`、`move` |
| SQL / 云 | `cloud_sql_execute_sql`、`cloud_sql_update_schema`、`deploy_firebase`、`set_up_cloud_sql`、`set_up_firebase` |
| MCP | `mcp_tool` |
| 子代理 | `invoke_subagent` |

**⏳ 仍需真机确认**：上表「文件写」一栏哪个才是 agent 实际写文件的步骤（`propose_code` 最可能）。

**处置（fail-safe，不等实测即可安全落地）**：WS3 的 matcher 用正则一次覆盖全部候选
（`propose_code|file_change|write_blob|edit_notebook|delete_directory|move`）——多跑几次 guard 无害，漏拦才有害；
真机确认后再收窄。确认前 `cto-doctor` 对 agy 文件写守护显示「候选覆盖，未经真机确认」，**不得标 ✓**。

**影响**：WS3 全部步骤（matcher 分组从 2 组扩到 4 组：shell 类 / git 类 / 文件类 / mcp+sql 类）、eval 100。

## ✅ spike-9（计划外，实证）— 写含红线字面量的文档必须用 Write 工具，不能用 Bash heredoc

**现象**：本文件第一次用 `cat > ... <<'EOF'` 写入时，被自己的 **bypass-guard 拦下**（`BLOCKED: 检测到 hook/pre-commit 绕过尝试`）。

**根因**：正文讨论绕过面时出现了红线字面量（如 pre-commit 跳过 flag、`core.hooksPath`）。
ADR-010 裁定 bypass-guard **保持广义 token + 剥引号归一化、不做读/写 carve-out**（3 轮 9 agent 对抗验证证明 static regex
无法安全区分），因此 heredoc 正文也在扫描面内 —— 这是**按设计的 fail-safe，不是 bug**。
（对照 learned rule `2026-05-20-guard-scan-strip-noncode`：destructive-action-guard 有剥 heredoc 层，bypass-guard 有意没有。）

**结论 / 操作规程**（与 memory 中 v4.4b 的教训一致，此处固化为仓库事实）：

- 写**含红线字面量的文档**（SPIKES / handbook / learned rules / ADR）→ 用 **Write / Edit 工具**，不要用 Bash heredoc。
- commit message 或 PR body 含红线字面量 → 走 `-F <file>` / `--body-file`，不要内联到命令串。
- 需要在 Bash 里诊断这些字面量 → 用 Grep/Read 工具，或先写脚本文件再执行。

**影响**：WS5/WS7 写文档时的操作方式；并作为 `.claude/rules/learned/` 的候选条目（v5 收尾时由 `/cto-evolve` 定夺，本轮不自动写入）。
