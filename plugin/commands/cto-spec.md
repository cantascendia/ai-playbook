# Spec

目标：$ARGUMENTS

一个功能一个文件：`docs/specs/<YYYY-MM-DD>-<slug>.md`。参数是已有 spec 路径时，读它并继续推进下一段。

## 写之前

- 读相关代码和 `docs/STATUS.md`，**基于读到的东西写**，不假设
- 需求本身有问题（目标不清、方案明显更差、和现有架构冲突）→ 先指出来

## 文件结构

```markdown
# <功能名>
状态：draft | approved | done

## 为什么
一段话：问题、谁受影响、不做的代价。

## 做什么
- 行为描述（输入 → 输出，含边界和失败路径）
- 不做什么（明确排除项）

## 验收
每条都能机器验证：命令 + 期望结果。

## 方案
- 改哪些文件、数据/接口怎么变
- 风险 + 回滚方式
- 哪些步骤先写测试（高风险路径必须先写测试、测试经 review 后再实现）

## 任务
- [ ] T1 … （每条：文件 + 完成标准；可并行的标出来）
```

## 节奏

1. 写完「为什么 / 做什么 / 验收」→ **停下给用户看**，确认后把状态改为 `approved`
2. 再写「方案 / 任务」，然后直接开工
3. 每完成一项勾掉并 commit；全部完成改为 `done`

改动涉及 auth / 支付 / secrets / migration / infra / CI 定义时，第 1 步不能跳过，合并前跑 `/cto-review`。
