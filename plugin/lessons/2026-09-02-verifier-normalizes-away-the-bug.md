# Learned Rule: 検証器が「正規化してから比べる」と、正規化前の壊れ方は永久に見えない

**学到的教训**: robotemi.jp の `.htaccess` で、日本語スラッグ 26 本の 301 が
`^/%25e6%25b5%25b7…$` という**一生当たらない**正規表現になっていた。
原因は `encodeURI()` —— WordPress の日本語スラッグは REST の時点で既に
`%e6%b5%b7…` なので、もう一度通すと `%` 自体が `%25` に化ける。

**これを 4 本の検証器が全部 PASS にした。** 公開前点検は「転送先が実在するか」を
見るとき path を `decodeURI()` してから探す。だから**壊れた側も正しい側も
同じ文字列に潰れる**。実際にサーバーへ投げる確認器を新しく書いて初めて出た。

## 触发场景

- 検証器が比較の前に `decodeURI` / `toLowerCase` / `trim` / `normalize('NFC')` /
  末尾スラッシュの除去 などを掛けている
- 比べる対象が「機械が literal として食う文字列」（正規表現・URL・パス・鍵）
- 「生成器と検証器が同じ正規化関数を共有している」構図（同じ盲点を持つ）

## 应该怎么做

1. **正規化は「比較のため」だけに使い、生成物そのものは生で 1 度は見る。**
   例: 転送規則なら「規則の文字列が台帳の path と**バイト一致**するか」を別に見る。
2. **層の違う確認器を 1 本足す。** ファイルを読む検証器と、
   実際に動かして投げる確認器は**別のものを捕まえる**。片方だけでは足りない。
3. **既に符号化されている文字列を再符号化しない共有関数を作る**:
   ```js
   export const encPath = (p) => String(p)
     .split(/(%[0-9a-fA-F]{2})/)
     .map((s, i) => (i % 2 ? s : encodeURI(s)))
     .join('')
   ```
   そのうえで **grep で `encodeURI(` を全掃き**して置き換える（1 か所直して終わりにしない）。
4. **壊れ方そのものを検証器の項目にする**。この件なら「規則の中に `%25` が出たら NG」。
   原因を直したら、同時に「その原因の痕跡」を機械が見張るようにする。

## 避免什么

- ❌ 「検証器が全部 PASS だから配信物は正しい」と結論する
  （検証器が見ていない軸は、PASS の数では埋まらない）
- ❌ 生成側と検証側で同じ正規化ヘルパーを共有したまま「独立に確認した」と言う
- ❌ 符号化済みかもしれない文字列に素の `encodeURI` / `encodeURIComponent` を掛ける
